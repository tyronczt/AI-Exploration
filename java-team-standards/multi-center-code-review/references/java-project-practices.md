## 1. 模块边界要能验证

**团队规则 ARCH-001**：先给出本次涉及模块的公开入口、内部实现、允许依赖与事实写入方，再决定包或 Maven 模块。应用服务可调用本模块能力及其他模块的公开契约，不直接使用对方 Mapper、DO、内部 Service 或内部 Spring Bean；同进程不为隔离目录额外增加 RPC。

| 决策 | 默认处理 | 何时升级 |
| --- | --- | --- |
| 包还是 Maven 模块 | 单部署单元内按业务包划分；现有工程结构优先 | 编译隔离、独立发布或实际复用需求明确时再拆模块 |
| Service 是否需要接口 | 单实现的内部编排可直接用类 | 确有跨模块公开契约或外部能力隔离时定义最小接口，即使暂时只有一个实现 |
| 外部能力端口 | 接口由使用方业务语义定义，适配器实现技术调用 | 需要隔离 SDK、远端系统或复杂领域存储时采用；简单 CRUD 不强加 Gateway/Repository 双层 |
| 架构门禁 | 复用已有 ArchUnit、Modulith 或项目检查；无工具时限定范围检查 import、依赖及调用 | 边界反复被破坏、有可维护的规则后，经选型再增加依赖；不能把 rg 检索报告成完整架构证明 |

端口的方法应表达业务需求，例如“查原操作结果”，而不是暴露 SDK Request、ORM Wrapper 或无边界的通用 execute。已采用领域模型时，纯业务规则不直接依赖 Controller、持久化实现、HTTP 客户端或静态 ApplicationContext 查找；依赖从已有构造/装配边界显式提供。不要因此给普通 CRUD 造一层空领域模型。

不能为了消除循环依赖把双方全部业务搬进 common；先判断事实归属、调用方向和公开契约。公共模块只容纳语义相同且稳定的能力。反射、字符串 Bean 查找和任意 ApplicationContext.getBean 不作为绕过依赖规则的出口。

**验收**：采用自动门禁时，在临时副本加入一次“模块 A 调用 B 内部 Mapper”或循环依赖，证明检查失败，再恢复并通过；记录实际扫描的包、排除范围与例外。只有目录名称、注释、空测试方法或被注释的断言，不能报告“架构约束已生效”。存量例外限定到实际依赖边，不为通过检查把整个业务包排除。

## 2. 用例编排与业务规则分开

COLA 的 application/domain/gateway 提供职责切分线索；沿目标已有 Controller、Service、Mapper/Repository 命名及 Query/VO 与内部 DTO 边界，按真实用途转换，不强制每个用例配 CmdExe/QryExe 或替换为 COLA 响应对象。

- **Controller/消息入口**处理协议、可信上下文和边界转换；同一业务用例从 HTTP、消息、任务进入时复用同一规则，不复制三个状态判断分支。
- **应用服务**协调授权、加载/保存、事务及副作用。方法按业务动作命名；当一个 Service 包含多项独立用例时按职责拆分，不按代码行数或一条 SQL 一个类拆分。
- **领域行为（按需）**集中维护复杂不变量；批准、预占、关闭通过带前置条件的业务方法表达，避免外部随意 setStatus/setBalance 绕过规则。数据库条件更新仍负责多请求竞争，内存对象校验不替代 CAS。
- **值对象（按需）**在金额与币种、区间等反复出现且有联合不变量时才创建；保持不可变或受控修改，明确 equals/hashCode、精度、单位和空值。不为每个 String/Long 包一层类；也不从别的项目复制名为 Money 的类型就宣称金额安全。
- **查询**可按只读 DTO/投影获取需要的字段，不必加载完整聚合；读写方法职责分开不等于必须建设 CQRS、双库或事件溯源。任何投影仍保留主体范围及分页 total 口径。

以“退款申请”为职责示意：入口转换 Query → 用例核验授权与原操作 → 在同一预算记录上原子预占并落退款意图 → 提交后调用外部能力或按既有任务派发 → 返回 DTO 再转 VO。费率/额度规则可以抽成纯计算；不能把跨网络调用和 UNKNOWN 恢复藏进一个声称“无副作用”的领域方法。此处是责任分配示意，不是可直接运行的支付实现。

异常保持现有 ERR-001/REMOTE-001 分类：业务拒绝、依赖失败、结果未知不能合成一个“失败”码。适配器保留 cause 并转换外部协议，统一出口返回安全错误；禁止通用 AOP catch-all 吞异常后返回成功或绕过事务回滚。采用 BizException/SysException 名称本身不证明分类、HTTP 状态和重试行为正确。

## 3. 扩展点先有变化，再选机制

**团队规则 EXT-001**：只有同一用例已有多个真实策略且变化边界明确时才抽扩展点。简单稳定分支用现有 if/switch；已有多个策略时优先项目当前策略接口或 Spring 注入列表/Map，不因参考 COLA 就引入新的扩展框架。扩展点封装“变化的业务计算/适配”，共同授权、幂等、审计和事务留在统一用例边界。

扩展契约写清：选择键来源、各策略适用范围、无匹配、多匹配、允许的默认行为、输入/返回/错误语义、是否有副作用。租户、渠道或产品键从可信配置及授权关系确定，不能让请求自由指定任意实现类或 Bean。

| 情况 | 团队要求 | 验收样例 |
| --- | --- | --- |
| 精确匹配 | 同一有效选择键得到确定策略，公共校验仍执行 | 两个合法产品各命中预期策略，越权主体被拒绝 |
| 无匹配 | 按业务契约报不支持；只有明确等价且获准的默认策略才回退 | 未配置产品不能默默走另一个支付渠道/费率 |
| 重复注册/多匹配 | 固定注册表启动时失败；动态配置发布前验证并原子切换 | 两个实现声明相同键，不能后注册覆盖前者 |
| 策略执行失败 | 分类报告；不把执行异常当成“查找不到策略”再回退 | 远程结果未知沿原操作查询，不改路由重做副作用 |
| 配置变更 | 进行中的有副作用操作保存决定所需策略版本/关键快照 | 重试复用原决定，配置更新不改写历史意图 |

Spring 单例策略不在成员字段保存当前请求、租户或可变金额；共享缓存/注册表说明并发与更新方式，单次上下文沿参数传递。扩展实现必须遵守同一超时、幂等和异常契约，不允许某个实现跳过公共安全检查。

COLA 的扩展查找具有默认场景回退，注册实现检查坐标重复。这说明“采用扩展框架”之前仍须确定路由政策；**本团队不默认采纳业务回退**。规则依据与代码入口见第 6 节，不复制整套扩展框架。

## 4. 状态机与事件不替代持久化保护

采用状态机前先列出当前状态、事件、条件、目标状态、同号重复和副作用。少量稳定状态可用枚举与显式分支；引入库时仍须明确拒绝、无转换和异常结果，不能把“返回原状态”当成成功。

COLA 本次核验的 `StateMachineImpl` 接收源状态并返回目标状态；其 `verify(state,event)` 检查是否存在事件转换，不接收业务上下文，也不完成条件、持久化或幂等校验。团队因此要求：

1. 从权威存储读取状态及版本；内存路由只产生候选决定。
2. 以旧状态/版本、主体与必要预算条件完成原子写入，检查影响行数；失败后重新核验，不盲目覆盖。
3. 条件判断保持无副作用。Action 若执行写入或远程调用，必须说明与状态保存的顺序、崩溃窗口和恢复；不能“先付款后 CAS 失败”再重试付款。优先复用现有持久化意图与派发机制。
4. 测试合法/非法转换、条件不满足、重复事件、并发竞争和执行后响应丢失。规则图或可视化只描述允许关系，不证明实际业务已受保护。

模块事件先说明采用哪种交付语义：同步处理的失败与事务关系、提交后处理的失败责任，或已接入的可靠发布/消费机制。异步注解和提交后监听本身不证明崩溃后可恢复。需要可靠交付时核验实际持久化配置、原事务写入、重试入口、消费幂等及积压告警；已有可靠机制满足需求就复用，不重复建设。

Spring Modulith 的事件发布登记是可选能力，是否持久化、如何重投由实际依赖/配置决定。引入它不等于业务副作用恰好执行一次，也不自动替代跨服务 MQ、幂等和失败补偿。验收至少包含原事务回滚、监听失败、进程重启、重复投递和消费者升级后的事件兼容。

## 5. 测试证明什么就报告什么

沿用 CHECK-001：测试层次由本次风险决定，不要求每个方法都写三套测试；框架注解、包名和版本以目标项目实际依赖为准。

| 待证明行为 | 最小合适验证 | 不能据此宣称 |
| --- | --- | --- |
| 纯规则/策略 | 普通单测覆盖边界、非法输入和策略选择，不启动完整 Spring | 已验证数据库事务、权限过滤链 |
| Web 契约 | 现有 MVC 切片或实际 HTTP；验证绑定、错误、JSON 与适用安全链 | Mock Service 已证明真实 SQL/资源权限；关闭过滤器后的测试已证明授权 |
| 存储与并发 | 目标数据库版本的隔离实例验证唯一性、条件更新、提交/回滚及映射 | H2/mock 证明 MySQL collation、锁与约束完全一致 |
| 模块接口 | 已有模块测试或最小集成；模拟明确外部边界，核验输入/输出契约 | mock 掉全部内部逻辑后证明了模块实际业务 |
| 第三方适配 | 受控协议服务模拟超时、错误、响应丢失等；必要时授权沙箱联调 | 模拟服务器证明真实机构已经支持或接通 |
| 架构/构建门禁 | 实际绑定的命令、故意违规失败样例、恢复后成功与执行报告 | 插件出现在 pom/pluginManagement 中就已执行，零测试等于测试通过 |

使用事务回滚型测试时，另选最小提交场景检查 after-commit 监听、真实提交时约束及跨线程行为；不能让测试事务掩盖生产提交边界。时间/随机性导致用例不稳定时，复用已有 Clock、固定输入和有界等待，避免依赖当前系统时间与长 sleep。

保持现有“测试文件仅本地验证、不提交 Git”的项目要求；仍报告验证命令、环境、断言/失败与可复查结果，不能因此伪称已有 CI 回归。文档更新只做链接、安装映射及包一致性校验；本轮没有运行这三个上游项目，也没有为参考工程新增运行时依赖或架构门禁。

## 7. 对照工程推进进度与逐点确认

**适用**：用户要求“根据技术文档梳理进度”“先完善已确认代码”“参照现有工程继续开发”。按 REQ-001、CHECK-001 推进，不把进度整理变成必须先答完全部问题的流程。

### 7.1 先确认实际完成到哪一层

从用户指定文档的能力清单出发，按相关入口、调用链、配置和当前验证报告核对；复用现有进度文档，不从页面、接口数量或目录结构计算完成百分比。没有 Git 时可用本次文件差异/快照与验证记录，不为此创建仓库或空记忆文件。

### 9.1 目录、命名与调用边界

采用本节示意布局时，业务位于 `<应用根包>/modules/<领域>/`；目标已有目录优先，只建立有实际内容的目录：

| 职责 | 领域内位置 | 边界 |
| --- | --- | --- |
| 同中心公开入口和协议 | api/facade、api/dto；公开枚举在 api/dto/enums | 只暴露必要 Facade/DTO，DO 不进入协议 |
| HTTP、请求、响应 | internal/web、internal/web/query、internal/web/vo | Controller 校验及纯转换；简单 Query 可拆业务参数，DTO 结果映射 VO，允许已确认基础类型/公共分页包装，不访问数据库或任务设施 |
| 用例、内部或远端协议模型 | internal/application、internal/application/dto | Service 可使用本领域 Mapper/DO，不依赖 Web 类型 |
| 状态、业务错误码 | internal/domain/enums | 纯领域规则不依赖 Spring、Web、ORM 或外部设施 |
| 表映射、Mapper、HTTP Client | internal/infrastructure/persistence/dataobject、internal/infrastructure/persistence/mapper、internal/infrastructure/client | 不反向依赖 Web，不公开 DO、ORM Wrapper 或 SDK 模型 |

Mapper XML 在 `src/main/resources/mapper/<领域>/`，与 Mapper 同名；业务 SQL 在所属中心 `db/sql/`。根包留启动类，必要装配在 `config/`，参数在 `config/properties/`。既有项目目录优先；移动按第 8 节同步扫描、XML、引用与装配，不新增空目录、占位 `.gitkeep` 或重复 `package-info.java`。

- 本领域：Controller/TaskHandler 可注入 Service 实现类；普通 CRUD 不强制 Service 接口、聚合、Repository、Converter 或 Gateway。复杂不变量或公开契约确有需要时再增加。

### 9.2 公共组件、幂等与事务

先核对目标真实依赖、版本、Bean 装配、表结构、连接、配置和调用。以下组件名称与协议是一组可选约定；仅目标确认采用相应实现时执行，其他同名组件按实际协议核验，不为其他工程新增这些组件：

| 已有入口 | 实现或审查要点 |
| --- | --- |
| SnowflakeIdGenerator、JsonStringId | 注入发号器调用 nextId；Java/数据库保留 long/BIGINT，对外字符串，前端不转 Number；核验节点/时钟保护，不清空已使用的节点登记 |
| IdempotencyKey、Idempotent、IdempotentIdResult | Controller 校验键，Service 的可代理 public 非 final 实例方法使用稳定操作名并返回结果；参数只放决定业务结果的值 |
| JdbcDeduplication | 服务身份入口由业务显式构造可信主体、组织和操作范围；组件只校验 scope 形式，不自动完成身份或资源授权 |
| IdempotentOperation | 持久操作/任务编号生成跨中心写请求键；同单据的多次动作区分各次操作，重试/重启复用原键，不用内容变化换键 |
| CurrentCaller | 从已验证令牌读身份/组织，业务检查动作和资源归属；服务令牌不伪装用户组织，客户端组织头不替代身份 |
| PlatformClient | Service 注入声明式 HTTP 接口，复用服务身份、请求标识、超时、隔离和响应处理；不重包 HttpClient、不手传或转发用户令牌、不盲目叠加重试 |
| NamespacedRedis、RedisGuards | 复用中心前缀、TTL、限流，失败由业务拒绝；Redis 不是权威事实，不替代持久幂等 |
| JdbcWorkStore、OutboxEvents | 业务状态与任务/Outbox 在本库同事务登记；任务用 consumePayload，MQ 用 consume 校验、去重和本地事务 |
| CosObjectStorage | 私有文件先验权限，上传在数据库事务外，对象键/内容可安全重试；短期签名 URL 不进入日志、文档或 Git |
| OperationAudit、PageQuery、MybatisPages、ApiResponses | 复用审计、分页和成功响应入口，保留权限与筛选口径；审计能力以实际 sink 为准 |

已采用本节 `@Idempotent` 实现时，它经 `JdbcDeduplication` 和同数据源的本地 JDBC 事务管理器管理事务，拒绝方法/类再加 `@Transactional`；不再传 key、手拼摘要或重放结果。通过注入的 Spring 代理调用，不用 this 自调用证明切面生效，也不宣称每次强制 REQUIRES_NEW。其他事务实现仍按 TX-001 核验，不能机械删除注解。

本节用户注解协议示例的作用域是“操作名 + 组织”，不含用户 ID；需要可信用户和组织，但不提供用户级去重隔离，业务权限独立校验。键为 1～100 位字母、数字或 ._:-；操作名为 1～80 位字母、数字或 ._-，应用内唯一且发布后稳定。同作用域同键内容不一致时拒绝；业务重复另用业务规则和唯一约束保护。未采用该实现的目标以实际键协议为准。

新操作新键，重试复用原键；操作名、任务类型和消费者标识稳定。HTTP、COS 上传和直接 MQ 发送不包在上述本地业务事务中；外部操作仅在原操作号、幂等保障和已确认协议允许时重试，结果未知先沿原操作查证。任务/Outbox 提交、调度领取与外部执行分开；DEAD/死信有恢复责任，不承诺跨系统恰好一次或自动补偿。@XxlJob 只登记入口，持续调度还需实际配置。

本节 `OperationAudit` 示例默认由 `Slf4jAuditRecorder` 写日志，可替换 `AuditRecorder`；不自动建立数据库审计，不等于资金审计账。默认记主体、请求标识、动作、资源编号、耗时、结果和异常类型，不记参数、返回体、异常消息或签名 URL。没有资源编号时不把标题作编号；审计 sink 和组织字段按目标真实契约核验。

### 9.3 HTTP、配置与数据

采用本节安全路由示意时，用户入口 `/api/v1/**` 与中心间 `/internal/v1/**` 分开；服务 JWT 核验受众、路径、方法、主体白名单和 scope，业务继续校验资源归属。目标已有路径与身份协议优先，不为联调关闭鉴权；X-Request-Id 只关联日志，不替代幂等键。

采用本节 Web 包装示意时，成功用 `ApiResponse<T>`，失败用非 2xx 的 `ProblemDetail`、中文提示并脱敏 5xx；允许已确认的基础类型和 `PageResult<VO>`，禁止内部 DTO/DO 或 ORM 页对象。其他项目保持已确认 Query/VO、HTTP 方法、响应和错误兼容性，不因示例改已有接口。

- SQL 归所属中心，公共技术表脚本归 common 模块；建表和迁移按目标既有流程及授权，不擅自自动建表，不新增或删除现有迁移工具。
- 数据库/Nacos 写入遵循当前授权；读取配置不构成写入权限。不为每项业务增加 profile、开关或 YAML。
- Nacos 导入优先级、重启和环境变量占位符按实际配置核验；`MP_*` 不会自动覆盖写死的 Nacos 值。架构/契约配置随源码保存，不上传 Nacos、不打进业务运行 JAR。
- 密码、令牌、私钥、签名 URL 不进入输出、示例或 Git；不把 `.local/auth`、节点登记或联调凭据当临时垃圾清理。
- version、状态条件和其他并发保护按目标实际契约核验；不因其他项目移除 version 而删除本目标已有保护，也不向已确认移除通用 version 的目标加列。时间命名、标识比较、deleted、金额、资金事实与删除政策均按各目标确认版本，不复制示例业务政策。

### 9.4 架构登记、契约与验证

仅目标已接入相应门禁或等效机制时同步登记，不为普通字段修改安装整套构建工具：

| 变更 | 同步和检查 |
| --- | --- |
| 新领域或同中心依赖方向 | 更新 architecture-modules.yaml，应用键等于 artifactId、root-package 对应根包；保留已有方向，拒绝重复键/循环/未登记类和无实际类的登记 |
| 新独立应用 | 根 POM、真实架构插件及自身 contracts 同步；工具依赖 scope 按实际绑定和运行制品核验，纯启动骨架可按已确认布局登记为空 |
| 公开 HTTP/事件 | current.yaml 同步字段、传输类型、required、Java 绑定、路由/方法或事件类型/版本 |
| 纯 Java 更名 | 更新 current 的 java-type 与调用方，历史 baseline 保留，协议仍参与兼容比较 |
| 发布新契约基线 | baseline.yaml 仅在确认新发布基线后更新，不复制 current 绕过兼容检查 |

请求可以加可选字段或放宽要求，不能增加必填负担；响应/事件不删字段、换类型或放松已承诺的必填保证。路由/方法不悄悄变化，不复用事件版本改变协议；不兼容变更按确认的版本与迁移方案处理。

核验静态门禁实际覆盖范围，已登记协议不代表穷尽所有 Controller、嵌套类型、反射字符串或 SQL 跨库访问。新协议主动登记，复杂结构确认工具是否支持；静态门禁不替代接口授权、数据库账号范围与真实行为验证。

构建命令按目标真实绑定阶段选择。例如门禁绑定 Maven prepare-package 时，package/verify 会到达该阶段，compile/test 不会；pluginManagement 声明不等于子模块实际启用。按受影响范围运行根 `mvn clean verify` 或 `mvn -pl <受影响应用> -am clean verify`，避免旧工具 JAR/class 掩盖遗漏，不将示例命令当成所有工程的保证。

测试源码/资源遵循目标 Git 忽略和提交约定，不擅自取消忽略或删除；跨机器先同步同版本测试。`-Dmaven.test.skip=true`、缺失或零测试只能报告相应构建/门禁，不能报告测试通过。交付消息说明验证结果，不为一次检查新增报告文档。

### 9.5 采纳与验收边界
