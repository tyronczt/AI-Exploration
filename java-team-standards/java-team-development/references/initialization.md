# 初始化决策与验收

没有真实业务模块时，先确定一个能运行和验证的工程切片。不要从“多个中台”直接推导出多个服务、多个数据库或统一基础框架。

## 1. 在项目中留下已确认的决定

使用项目已有决策文档；没有时，在用户授权初始化方案或工程后生成 `docs/engineering-baseline.md`。安装规范不会自动创建它。每项记录“值 / 已确认、建议或待定 / 依据与日期”，未决项可以保留，不伪造确认。

| 决策项 | 要写清的内容 |
| --- | --- |
| 技术基线 | JDK、Spring Boot、构建工具具体版本及本次受影响组合；按完整规范 3.7 区分技术兼容、生成器支持与已确认选择 |
| 依赖/制品 | parent/BOM、实际依赖/插件与 scope、固定发布版本及仓库来源；验收完整规范 3.6、16.5，不靠 dependencyManagement 推定已引入 |
| 工程形态 | 根包、实际模块、部署单元；先单模块或模块化单体的依据 |
| 模块与扩展 | 公开契约、内部实现、允许依赖与写入责任；是否存在真实多策略及匹配/回退政策。读取 [Java 项目实践](../../multi-center-code-review/references/java-project-practices.md)，不因 COLA 示例生成空层或自动升级依赖 |
| 数据访问 | 数据库、ORM、迁移工具；未决定时不引入依赖或生成空 Mapper |
| MySQL 表结构 | 精确版本、ID 策略、引擎/字符集/collation、时间约定、表职责及字段/索引；生成 DDL 前读取 [DDL-001 建表规范](../../multi-center-code-review/references/mysql-schema.md)，不自动堆叠外键或触发器 |
| Web 契约 | 普通 class + Lombok、Query/DTO/VO 位置；业务请求参数超过 3 个用 POST JSON，3 个及以内的简单只读查询可用 GET；参数计数及复杂结构按完整规范 6.2；响应包装、HTTP 状态与错误码 |
| 前后端线上的协议 | 已采用代码生成时按完整规范 6.7 记录契约权威输入、生成器版本/命令和实际消费方；WEB-003 的 UTF-8/媒体类型、字段类型与空值、ID/金额精度、日期/时区、枚举演进、请求上限、缓存/跳转；实际报文与 JS/浏览器验收见完整规范 6.4～6.6 |
| 序列化契约 | Serializable/UID 团队约定；实际 JSON/RPC/缓存/消息序列化器、构造绑定、泛型与新旧读取策略 |
| 分页 | 页码起点、默认值、字段缺失/null 与缺失请求体策略、上限、越界策略、总数口径、稳定排序；验收见 WEB-002 |
| 权限 | 身份来源、动作权限、资源归属、适用的 CSRF，以及查不到与无权访问的返回政策；不直接照搬教学认证配置 |
| 配置与部署边界 | 配置注册/校验、单位、profile/环境变量覆盖、重启及轮换；有前端时追加完整规范 11.2.1 的 API 地址/端口/代理/Origin 联动与公开/秘密边界，按 CONFIG-001、AUTH-001、OBS-001 |
| 副作用 | 哪些操作写事实；事务、幂等键、重复结果和失败恢复的责任方 |
| 中间件 | 现有需求与引入依据；不因“以后可能需要”引入 MQ、Redis 或分布式锁 |
| Redis（实际采用时） | 按 REDIS-001 读取 [Redis 专项规范](../../multi-center-code-review/references/redis-standards.md)：实际版本/拓扑、用途与权威数据、Key/协议/TTL、容量/时限、锁或 Stream 的持久化保护与恢复；不使用默认连接/示例阈值替代已确认配置 |
| 工程检查 | 实际编译、格式/注释检查及行为命令；按完整规范 16.6 绑定版本、输入、制品和环境，分开生成/构建/运行、真实联调与上线，核对注释业务准确性 |
| 模板更新（实际使用时） | 按完整规范 3.8 记录生成来源、受管路径和落盘基线；差异计划、手改/删除/冲突保护、并发复查与失败/中断恢复，不因初始化引入新生成器 |
| Java 与运行场景 | JAVA-001 的相关值/日期/集合/异常边界，8.2 并发、10.4 SQL/ORM、14.1 日志、18.1 JVM；按 16.5 选择本切片验收，不机械生成所有测试或新增设施 |
| 例外 | 规则编号、原因、替代保护、负责人和复核条件 |

在 AGENTS.md 受管区块外补充版本、命令和决策文档链接；不要复制整份决策文档。团队格式规则和业务政策分别维护。

实现具体业务需求时按 REQ-001 对应输入、范围、期望及验收；小需求在回复中说明即可，复杂需求沿用已有需求文档。缺陷修复按 BUG-001 留失败证据及同断言复验，不将工程基线文档当作每项业务需求已经确认的证明。

## 2. 最小参考工程

源码位于 [examples/reference-service](https://github.com/tyronczt/AI-Exploration/tree/main/java-team-standards/examples/reference-service)，独立 ZIP 同时包含它。仅安装规范不会复制或运行工程；用户明确要求初始化/运行参考工程时，从同一版本包取出。

这是 Java 21 + Spring Boot 3.5.16 + Maven 的单模块、只读组织查询示例。它演示 Query → DTO → VO、分页、校验、统一错误和动作/资源权限；组织仅为教学对象，不预设真实中台职责。

示例分页保留已确认的 `POST /api/reference/organizations/page` JSON 契约，演示请求体绑定和 CSRF；当前仅有两个分页参数，不表示分页必须 POST。新接口按业务参数数量选择；详情使用 GET。示例契约：响应 `code/message/data`；成功码 `OK`；分页 `pageNo` 从 1 开始，默认 20 条，上限 100，超限拒绝，按创建时间降序再按 ID 降序；列表 `items/total/pageNo/pageSize`。这些是示例已定值，新项目须单独采用或调整。

身份采用环境变量密码和 Spring Security HTTP Basic，仅绑定本机。正式系统应接入已确认身份服务；内存数据不证明 SQL、事务、持久化幂等或生产认证已完成。

## 3. 工程验收

- 编译、打包与静态检查成功；故意加入星号导入后检查失败，恢复后重新通过，证明检查实际执行。
- 实际启动并发送 HTTP 请求，验证 Query 绑定、分页默认/边界/非法值、稳定排序、统一错误。
- 未登录访问令牌/详情接口得到 401；POST 先验证 CSRF，缺失或错误令牌得到 403，合法令牌再检查认证与动作权限；不同企业互不可见；跨企业详情与不存在资源采用同一 404 策略。
- 明确记录测试数量。示例没有提交自动测试文件，不把 Maven 的零测试报告成“测试通过”；行为验证步骤见工程 README。
- 引入数据库或写入后，再用选定数据库验证唯一约束、条件更新、回滚、并发、幂等及异常恢复。参考工程的结果不覆盖这些项。

## 4. 验证规范是否真能帮助智能体

后续使用同一模型、工具、固定输入和工程基线，分别在有/无本规范的干净临时副本执行；每例建议重复 3 次，保留失败，不仅展示最佳输出。区分客户端发现、模型遵循与生成代码行为三类评测，不能用主动提供 Skill 的结果证明自动发现。小样本只反映当前条件。

固定任务、初始数据与判定材料见本规范包 evaluations/README.md，先执行 E1、E3、E4、E5；该维护文件不安装到业务工程，应从相同来源提交/制品的完整包取用。仅向受测智能体提供固定用户任务与必要原始材料，不提供评审专用答案、注入方法和判定表。若要比较新规则，再执行对应的 E11～E23。

| 编号 | 给智能体的真实任务 | 验收要点 |
| --- | --- | --- |
| E1 开发 | 给参考列表增加名称筛选 | Query 校验、DTO 转换；筛选和 total 均保留资源范围 |
| E2 开发 | 给详情增加展示字段 | VO 字段来源与注释准确；不暴露内部资源归属字段 |
| E3 审查 | 在临时副本删掉资源过滤，要求审查 diff | 指出 AUTH-001、真实行号和越权输入；不提示预设答案 |
| E4 审查 | 审查正常的只读实现 | 不要求 Outbox、幂等表、DDD 空层；没有证据不凑问题 |
| E5 安装 | 首装、重装，再手改受管文件后更新 | 无重复区块；原有内容保留；冲突不覆盖、不部分更新 |
| E6 DDL | 分别为 MySQL 5.7/8 设计商户请求记录表，再审查其唯一性和状态更新 | 新内部 ID 不自增，公共时间列 create_time/update_time；字符列继承表默认，ASCII/bin 例外有协议依据；金额单位及存量主键不被模板改写；验证大小写/尾空格幂等、主体范围内唯一；不滥用外键/触发器，说明 CHECK 差异和未验证项，不执行业务库 DDL |
| E7 逻辑删除 | 为已有管理表实现删除/恢复，并审查自写 JOIN 与业务号复用 | deleted 由服务端控制；过滤、权限与审计完整；删除竞争、重复请求、重建再次删除及恢复占号有验证；不向支付事实表机械加列，不声称注解覆盖所有 SQL |
| E8 模块 | 给同进程的另一个模块提供只读能力，再审查越界调用 | 走最小公开契约，不直接调用内部 Mapper/DO；不新增 RPC/空模块；已有门禁用越界样例证明失败 |
| E9 扩展 | 为已有两种产品规则增加第三种，并审查无匹配及重复键 | 复用现有策略或分支；选择键可信、重复配置拒绝；不凭默认策略隐藏错误；单例无请求状态 |
| E10 状态与事件 | 审查状态机 Action 执行远程写入，以及提交后监听失败的恢复 | 区分转换路由、CAS、副作用和持久化；覆盖重复、并发、响应丢失/重启边界，不把注解当作可靠交付证明 |
| E11 需求 | 给列表增加已明确的名称筛选，同时要求定义尚未确认的恢复行为 | 对应已确认需求与验收；继续独立筛选工作，恢复政策单列待确认，不扩大实现 |
| E12 修复 | 临时副本中的大页码查询异常，要求修复并留证据 | 失败复现、偏移根因、相关入口及同断言复验；不只编译或改 Controller 默认值 |
| E13 配置 | 评审配置类注册、零超时和 profile 覆盖材料 | CONFIG-001 的绑定、约束与部署覆盖证据；不混用 Boot 4 样例或声称文件修改已线上生效 |
| E14 代理 | 评审固定 Spring 6.2 的事务自调用及 protected 事务入口 | 区分内层传播失效、仍有效的外层事务与正常类代理入口；不按可见性机械报错 |
| E15 集合 | 评审 Stream.toList 返回后追加元素及只读对照样本 | 指出真实修改路径与异常；不将只读样本或 Collectors.toList 的未保证语义误报成已发生异常 |
| E16 Redis 扫描与锁 | 评审固定游标样本和租约到期后旧持有者释放 | 空批/重复与终止条件、原子 owner 校验及迟到业务写入边界；不误报安全释放对照 |
| E17 Stream | 评审先 ACK 后提交与提交后 ACK 的对照消费材料 | PEL 恢复、业务 eventId 防重、ACK 失败重投及裁剪窗口；不要求改 MQ 或推定未提供的生产端有缺陷 |
| E18 Java 基础 | 评审严格日期/排序的错误与安全对照 | 跨周所属年、非法闰日、排序极值证据；不误报严格解析/Integer.compare，不扩大为工具库重写 |
| E19 前后端 | 评审实际报文、JS 解析及允许跳转政策 | 大 ID 字符串与数值区别、偏移/无偏移、204/no-cache、精确 host 校验；保留正常对照和既定 GET |
| E20 SQL/Maven | 评审聚合映射、动态排序白名单及 dependencyManagement 材料 | COUNT/SUM/null、#{}/${} 真实差别、管理与引入区别；不误报安全排序或凭材料虚构数据库执行 |
| E21 组合与更新 | 评审固定脚手架支持范围和双方修改材料 | 区分生成器限制与框架能力；拒绝冲突、保护手改/删除，不能静默取消已确认认证或伪造基线 |
| E22 能力证据 | 评审源码变更、跳过测试与健康页记录 | 版本/范围不匹配不沿用通过；健康页/H2 不证明认证、MySQL/Redis 或上线；保留正常证据范围 |
| E23 生成与配置 | 评审契约/客户端类型及公开环境材料 | 陈旧客户端、大 ID、生产示例密码及客户端秘密边界；正常客户端与公开 API 地址不误报 |

每次记录规则版本/来源提交或制品哈希、工程基线与工作区状态、模型、客户端/工具版本、固定输入、产物、命令及判定证据；结果标为通过、失败、待核实或未执行。记录规则遗漏、误报、返工、用时及可取得的 token/费用；每种客户端分别核验发现和引用。成功启动模型或收集响应不算评测通过；修改规则后复验受影响任务，生成代码另做实际行为验证。上述是评测方案，工程 smoke 验证不等于已经完成这组智能体对照评测；普通开发和规范安装不自动执行模型评测。

## 5. 如何维护

真实任务反复出现且能复现的问题才升级为规则，单次偏好不自动写进 AGENTS.md。短入口保留导航，细节只维护在共用参考中。新增规则先给编号、适用条件、反例和验收；工具升级后复验受影响路径。

搜索相似 Skill 时按 [完整规范 20.7](../../multi-center-code-review/references/standards.md#207-skills-目录检索原始核验与采纳)使用阿里云 Skills、SkillsMP 等目录作为发现入口，回溯固定源码并核验项目版本；同源翻译去重，标注未核验与未采纳理由。只补已证明有决策价值的缺口，不随普通初始化搜索或安装整套第三方 Skill。

已有工程要求“梳理进度并继续”时读取 [进度与逐点确认](../../multi-center-code-review/references/java-project-practices.md#7-对照工程推进进度与逐点确认)，不要重新生成初始化方案：对照目标、代码与当轮证据，继续已确认独立工作，逐点保留缺口及已确认暂缓。用户要求文件按模块归属时再读 [包移动验收](../../multi-center-code-review/references/java-project-practices.md#8-按业务归属整理包与资源)，检查扫描/资源装配、干净构建和实际协议兼容；工程目录与测试数量不作业务闭环证据。

采用依据：[Spec Kit 计划模板](https://github.com/github/spec-kit/blob/main/templates/plan-template.md)用于记录技术上下文和复杂度依据；[HumanLayer 指令维护实践](https://www.humanlayer.dev/blog/writing-a-good-claude-md)用于短入口与按需读取；[上下文文件评估研究](https://arxiv.org/abs/2602.11988)提示需要实际任务对照，不能宣称增加规则必然提高效果。
